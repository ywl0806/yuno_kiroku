# 파이프라인 장애 시나리오

실제 코드 분석 기반으로 이미지/비디오 처리 파이프라인에서 발생 가능한 장애 시나리오를 정리한다.

> 각 시나리오 표기 기준
>
> - **심각도**: 🔴 High (데이터 손실/서비스 불가) · 🟡 Medium (일부 기능 누락) · 🟢 Low (일시적, 자동 복구)
> - **자동복구**: SQS 재시도, ECS 재기동 등으로 운영자 개입 없이 해결 가능한지 여부

---

## Stage 1 — Presigned URL 발급

### S1-01 · S3 Presigned URL 발급 실패

| 항목            | 내용                                                                                                                                                                                                                                                    |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **심각도**      | 🟡 Medium                                                                                                                                                                                                                                               |
| **트리거**      | DB INSERT 성공 후 `s3.GeneratePresignedPutURL()` 호출 실패 (S3 권한 오류, 네트워크 순단)                                                                                                                                                                |
| **현재 동작**   | API가 에러를 클라이언트에 반환. `media_items`, `media_files` 레코드는 이미 생성된 상태                                                                                                                                                                  |
| **영향**        | `upload_status = 01` 고아 레코드 누적. 클라이언트는 재시도 시 새 레코드가 또 생성됨                                                                                                                                                                     |
| **현재 완화책** | 없음. 24시간 이상 `pending` 레코드는 수동 정리 필요                                                                                                                                                                                                     |
| **해결책**      | URL 발급을 DB INSERT 이전으로 순서 변경 (Presigned URL 먼저 발급 → 성공 시 DB INSERT). 또는 DB INSERT와 URL 발급을 단일 트랜잭션으로 묶고 URL 발급 실패 시 롤백 처리. 추가로 24시간 이상 `upload_status = 01`인 레코드를 자동 삭제하는 스케줄 배치 구현 |

### S1-02 · 배치 발급 중 일부 항목 실패

| 항목            | 내용                                                                                                                                                                                                                          |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **심각도**      | 🟡 Medium                                                                                                                                                                                                                     |
| **트리거**      | 여러 파일을 루프로 처리하다가 중간 항목에서 S3 또는 DB 오류 발생                                                                                                                                                              |
| **현재 동작**   | 앞선 항목의 레코드는 이미 커밋된 상태로 남음. 에러 발생 항목 이후는 처리되지 않음                                                                                                                                             |

| **현재 완화책** | 없음. 클라이언트가 응답을 파싱해서 성공 항목만 업로드해야 함                                                                                                                                                                  |
| **해결책**      | 응답 구조를 `{ success: [...], failed: [...] }` 형태로 변경하여 클라이언트가 실패 항목을 명시적으로 인지하도록 수정. 각 항목을 독립적으로 처리하되 실패 시 해당 항목 DB 레코드를 롤백. 클라이언트는 실패 항목을 별도로 재시도 |

## Stage 2 — Resize Worker

> 코드: `server/internal/worker/services/resize_service.go`  
> 트리거 방식: S3 PutObject Event → HTTP POST `/resize` → **goroutine으로 비동기 처리**  
> (로컬 개발환경에서는 MinIO Webhook으로 대체)

### S2-01 · S3 원본 파일 다운로드 실패

| 항목            | 내용                                                                                                                                                                                                                                                              |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **심각도**      | 🟡 Medium                                                                                                                                                                                                                                                         |
| **자동복구**    | 불가 (S3 Event 재시도 없음)                                                                                                                                                                                                                                       |
| **트리거**      | `storage.GetFile()` 실패 (네트워크, IAM 권한, 파일 미존재)                                                                                                                                                                                                        |
| **현재 동작**   | `setFailed()` 호출 → `upload_status = 04`                                                                                                                                                                                                                         |
| **영향**        | 해당 미디어 처리 영구 중단. 수동 재처리 필요                                                                                                                                                                                                                      |
| **현재 완화책** | `upload_status = 04` 확인 후 수동으로 `/resize` 재호출 가능                                                                                                                                                                                                       |
| **해결책**      | S3 Event → SQS → Worker 구조로 전환하여 자동 재시도 지원 (근본적 해결). 단기적으로는 `upload_status = 04` 레코드에 대해 관리자 API 또는 배치로 자동 재처리 트리거 추가. 다운로드 실패 시 지수 백오프(exponential backoff)로 최대 3회 재시도 후 `setFailed()` 호출 |

| --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **심각도**      | 🟡 Medium                                                                                                                                                                                                                                                                  |

## Stage 3 — Video Processing Worker

> 코드: `server/internal/worker/video/video_processing_service.go`  
> SQS: `yuno-video-processing` · visibility timeout 900초 · maxReceiveCount 2회

### S3-01 · SQS 메시지 JSON 파싱 실패

| 항목            | 내용                                                                                                                                                                                                                                        |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **심각도**      | 🔴 High                                                                                                                                                                                                                                     |
| **자동복구**    | 불가                                                                                                                                                                                                                                        |
| **트리거**      | SQS 메시지 body가 유효하지 않은 JSON                                                                                                                                                                                                        |
| **현재 동작**   | `deleteMessage()` 즉시 호출 후 `continue` — **DLQ를 거치지 않고 메시지 영구 삭제**                                                                                                                                                          |
| **영향**        | 해당 동영상 처리 데이터 완전 손실. 재처리 불가                                                                                                                                                                                              |
| **현재 완화책** | 없음. 다른 에러 경로와 다르게 DLQ 미경유                                                                                                                                                                                                    |
| **해결책**      | JSON 파싱 실패 시 `deleteMessage()` 호출 제거 → SQS가 visibility timeout 후 재발행하여 maxReceiveCount 소진 시 DLQ로 자동 이동. DLQ 메시지는 원본 body를 보존하므로 수동 검사 후 재발행 가능. CloudWatch Metric으로 DLQ 메시지 수 알람 설정 |

| 항목            | 내용                                                                                                                                                                                              |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

### S3-03 · ffmpeg 처리 타임아웃 (30분 초과)

| 항목            | 내용                                                                                                                                                                                                                                                                                   |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

### S5-01 · Advisory Lock 무한 대기 (데드락)

| 항목            | 내용                                                                                                                                                                                                                                                                                |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **심각도**      | 🔴 High                                                                                                                                                                                                                                                                             |
| **자동복구**    | 불가                                                                                                                                                                                                                                                                                |

| **현재 동작**   | `TransactWithAdvisoryLock()` 내 타임아웃 설정 없음 → Go CLI 무한 대기 → Python subprocess 무한 대기                                                                                                                                                                                 |
